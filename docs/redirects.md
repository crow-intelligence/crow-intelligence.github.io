# Redirect map

Recovery map for the WordPress-era URLs and the retired Hungarian mini-site.

**Nothing here is live yet, and none of it can be.** The site is on GitHub Pages,
which cannot issue a 301: no server-side redirects, no custom headers, no
includes. These rules apply the moment Cloudflare sits in front of the domain.
Until then, this file is the deliverable.

Cloudflare's Free plan allows **10 Single Redirect rules**, and wildcards are
available on all plans. The rules below are written to be pasted into the
*Redirect Rules → Create rule → Single Redirect* wildcard interface as-is:
`Request URL` in the left field, `Target URL` in the right, status **301**,
*Preserve query string* **on** unless noted.

Ten slots, seven rules used.

---

## The rules

### 1. Dated blog posts → the blog subdomain

| | |
|---|---|
| **Request URL** | `https://crowintelligence.org/*/*/*/*` |
| **Target URL** | `https://blog.crowintelligence.org/${1}/${2}/${3}/${4}` |
| **Status** | 301 |

WordPress permalinks were `/YYYY/MM/DD/slug/`. Four wildcards rather than a
date-shaped pattern because Cloudflare's wildcard syntax matches path segments,
not character classes; the fourth segment carries the slug.

> **Never** collapse these to `/` or to `/blog/`. Google reads a mass redirect
> to an irrelevant target as a soft 404 and drops the URL anyway, which loses
> exactly the equity the redirect exists to preserve.

### 4. Author archives → the blog subdomain  `[PROVISIONAL]`

| | |
|---|---|
| **Request URL** | `https://crowintelligence.org/author/*` |
| **Target URL** | `https://blog.crowintelligence.org/author/${1}` |

> ⚠️ **Rules 2–4 are provisional and must not be pasted in as they stand.**
> They assume the WordPress install still serves `/category/…`, `/tag/…` and
> `/author/…` under those exact paths. Confirm each one on
> `blog.crowintelligence.org` first. Any taxonomy path that does not resolve
> there should point at `https://blog.crowintelligence.org/` instead —
> redirecting to a 404 gains nothing over serving one.

### 5. The retired Hungarian mini-site

| Request URL | Target URL | Status |
|---|---|---|
| `https://crowintelligence.org/hu/` | `https://crowintelligence.org/` | 301 |
| `https://crowintelligence.org/hu/portfolio.html` | `https://crowintelligence.org/portfolio.html` | 301 |

`/hu/` held average position 3.05 on 38 impressions — the best on the site —
which is why it is redirected and not deleted. Both paths currently serve
`noindex` meta-refresh stubs generated by Pelican (`content/pages/hu-*-redirect.md`);
**delete those two stubs once these rules are live**, so there is one redirect
rather than a 301 into a meta-refresh.

`/hu/rolunk/` appears in some notes but never existed in this repo or in the
build output. No rule.

## Interim cover

`404.html` at the repo root already carries a JavaScript redirect for legacy
WordPress paths. It is a client-side fallback, not a substitute: it passes no
link equity and only fires once the 404 has been served. Keep it until the
Cloudflare rules are live, then reassess.

## What the repo does *not* contain

The audit reported three WordPress-era pages still returning 200 on the apex —
`/2020/02/21/getting-started-with-sql/`, `/author/crowintelligenceteam/` and
`/portfolio-3/`. None of them exists in this repository:

```
grep -ri "wp-content\|wp-includes\|jetpack\|society6\|wp-json" .   # no matches
```

and there is no `20xx/`, `category/`, `tag/`, `author/`, `portfolio-*`,
`privacy-policy/`, `research/` or `au/` directory. The deploy workflow builds a
fresh artifact from an allowlist, so nothing WordPress-shaped can reach
production through it.

If those URLs really do return 200, they are being served from somewhere other
than this repo — worth confirming before the rules go live, since a redirect
rule cannot override a different origin.
