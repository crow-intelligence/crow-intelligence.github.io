# Redirect map

Rules to apply once Cloudflare sits in front of the domain. **Nothing here is live
yet, and none of it can be** — the site is on GitHub Pages, which cannot issue a
301: no server-side redirects, no custom headers, no includes.

Until then the paths below are served as `noindex` meta-refresh stubs generated by
Pelican (`Template: redirect`, see `pelican/content/pages/*-redirect.md`). A stub
passes no link equity, so these rules still matter.

Format: Cloudflare *Redirect Rules → Create rule → Single Redirect*, wildcard
interface. `Request URL` left, `Target URL` right, status **301**, *Preserve query
string* on.

## Withdrawn services

Both offers were retired on 2026-09-20 in favour of a single language-data
practice. They are redirected rather than 404'd because both were linked from
LinkedIn posts and outbound email.

| Request URL | Target URL | Status |
|---|---|---|
| `https://crowintelligence.org/services/ai-due-diligence.html` | `https://crowintelligence.org/services/language-insight.html` | 301 |
| `https://crowintelligence.org/services/ai-adoption-audit.html` | `https://crowintelligence.org/services/language-insight.html` | 301 |

Two exact paths, so one rule with two expressions rather than two rules.

**Once these are live, delete the two stub pages** — `pelican/content/pages/ai-due-diligence-redirect.md`
and `ai-adoption-audit-redirect.md` — along with the `services/ai-…` pattern in
`SITEMAP['exclude']` (`pelicanconf.py`). A 301 into a meta-refresh is one hop too
many.

> Both targets point at the replacement service, not at `/services.html`. A
> redirect to a hub is a weaker signal than a redirect to the page that actually
> answers the same question, and Google treats a mass redirect to a generic target
> as a soft 404.
